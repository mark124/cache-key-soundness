\begin{abstract}
GitHub Actions workflows often save a built Python environment to a cache and
restore it in later runs. Because the cache key alone decides when a saved
environment is reused, it is the only record of what that environment depends
on, and it must cover all of it. Build-systems research treats a missing input
as a correctness bug; research on CI caching has studied adoption, speed and
storage, but not whether keys are complete. We examined \ck{h.repos_sampled}
Python repositories. Of \ck{h.built_env_steps} cache steps that store a built
environment, \ck{h.unsound_steps} (\ck{h.unsound_pct_of_built}\%) use a key
without the exact Python version, in \ck{h.repos_any_unsound} of the
\ck{h.repos_caching_built_env} repositories that cache an environment at all.
\ck{h.unsound_with_skip_or_restore_keys} of those steps also skip installation
on a hit or fall back to a prefix key, the two routes by which our experiment
produced harm. In that controlled experiment on GitHub's runners, a key with
no Python version made a job set up for Python~3.13 run its tests on 3.11 and
pass, under pip, Poetry and uv. With only the minor version in the key, a
patch release broke the build under pip and Poetry, while uv rebuilt the
environment. The silent failure also occurs in practice: in one public
project's CI, \ck{w.wild_jobs_wrong_python} of \ck{w.wild_jobs_in_live_run} matrix jobs ran their tests
on the wrong Python and passed. We release a linter that flags incomplete keys. The fix is one
expression, and for pip and Poetry it keeps the time the cache saves. Code,
data and every number in this paper: \repourl.
\end{abstract}

\section{Introduction}

A CI service can save a folder at the end of one job and restore it at the
start of a later one. On GitHub Actions this is the \texttt{actions/cache}
action. A step names a folder and a key; if a saved copy with that key
exists, the action restores it and reports a hit. The action's own documentation then
shows the obvious next step: when the key hits, skip the install
step~\cite{actionscache}.

That is fine for a cache of downloaded packages. Package managers check what
they download, and the install step still runs. A \emph{built} environment is
different. A Python virtual environment remembers the interpreter that created
it, and its \texttt{python} command is a link to that interpreter. Compiled
packages inside it were built for that one interpreter version. Restoring it
under a different interpreter reuses a build whose inputs have changed. The cache key is what decides whether that happens.

Build-systems research already treats this as a bug: a saved result that
does not account for one of its inputs can produce a wrong
build~\cite{mokhov2018build,licker2019incorrect}. Bazel users call the same
property hermeticity~\cite{zheng2025hermeticity}. Research on CI caching asks
other questions. It asks how teams adopt and maintain
caching~\cite{hasan2026caching}, whether caching saves
time~\cite{ghaleb2026travis,bouzenia2024resource}, and which settings waste
storage or cause misses~\cite{urdih2026smells,khatami2024smells}. Closest to
our question, \citet{gallaba2022kotinos} avoid hand-written dependency
declarations altogether: their CI service infers dependencies and caches whole
build environments, because hand-maintained dependency graphs can be
under-specified and give incorrect builds. Practitioners know part of the
problem: a GitHub Action exists to change cache keys when a new Python patch
release leaves cached environments with ``broken symlinks or missing
libraries''~\cite{mckee2024detectpythons}, and a guide to caching virtual
environments puts the full Python version in the key~\cite{johnson2023venvcache}.
We found no study that measures how often the cache keys people write by hand
in GitHub Actions workflows cover what the cached folder depends on, or what
happens when they do not.

This paper makes three contributions.
\begin{enumerate}
\item A rule for when a cache key for a built Python environment is complete,
  plus a tool that checks workflow files against it (\S\ref{sec:sound}).
\item A count across \ck{h.repos_sampled} Python repositories of how often
  built environments get cached, and how often the key leaves out the Python
  version (\S\ref{sec:rq1}).
\item A controlled experiment that restores these caches under pip, Poetry and
  uv on GitHub's runners and records which Python the tests really ran on
  (\S\ref{sec:rq2}).
\end{enumerate}
We also look through commit history for signs that maintainers run into the
problem (\S\ref{sec:rq3}).

\section{Background}
\label{sec:bg}

\paragraph{How \texttt{actions/cache} matches.}
A cache step has a \texttt{key} and, optionally, a list of
\texttt{restore-keys}. If a saved entry has exactly the same key, it is restored
and the step's \texttt{cache-hit} output is \texttt{'true'}. If not, each
restore key is tried as a prefix: any saved key that starts with it counts,
newest first. A prefix match still restores the files, but
\texttt{cache-hit} is \texttt{'false'}. Every entry also has a hidden
\emph{version}. It is a hash of the compression tool and the list of cached
folders. Entries with different versions never match. That is why a Windows
cache is never restored on Linux~\cite{actionscache}.

\paragraph{What a virtual environment depends on.}
On GitHub's hosted runners, \texttt{actions/setup-python} installs each Python
under \texttt{/opt/hostedtoolcache/Python/X.Y.Z/}. The runner image in our
runs (\texttt{ubuntu-24.04}, version 20260920.314.1) carried exactly one patch
release of each minor version: 3.10.21, 3.11.16, 3.12.14, 3.13.15 and 3.14.7.
Every outcome file under \texttt{data/harm/} records this. A virtual
environment built on 3.12.10 links to
\texttt{/opt/hostedtoolcache/Python/3.12.10/x64/bin/python}. That path does not
exist on this image. An environment built on 3.11 links to the 3.11 install,
and that one does exist, because the image carries several minor versions side
by side. So a patch mismatch leaves a broken link, while a minor mismatch
leaves a working link to the wrong Python.

\section{When Is a Cache Key Complete?}
\label{sec:sound}

A cache key is \emph{complete} when it, together with the folder list that
\texttt{actions/cache} folds into the hidden version, determines everything
the cached folder depends on. For a built Python environment that is the exact
Python version, the dependency list, the operating system and the CPU
architecture. \ck{h.built_with_deps_hash} of the \ck{h.built_env_steps} keys
we studied hash a dependency file, \ck{h.built_hashing_lock_file} of them a
lock file. The hidden version is built only from the compression tool and the
folder list~\cite{actionscache}, so it separates Windows from Linux but not
one CPU architecture from another.

Our verdicts judge the Python version only, because that is the input our
experiment varies. We call a step \emph{sound} when its key pins the exact
Python version, and report the other inputs separately. Of the
\ck{h.sound_steps} sound keys, \ck{h.sound_with_deps_and_os} also hash a
dependency file and name the operating system, and \ck{h.sound_without_arch}
carry nothing that identifies the CPU architecture.

Our classifier (\texttt{cachekeys/analyze.py}) first works out what a cache
step stores. A \emph{built environment} is a virtual environment
(\texttt{.venv}, \texttt{venv*}, Poetry's \texttt{virtualenvs}), a
\texttt{.tox} or \texttt{.nox} folder, \texttt{site-packages}, the target of
\texttt{pip install -{}-user}, or the Python install folder itself. A
\emph{download store} is a package manager's cache of downloaded files. Each
built environment then gets one verdict:
\begin{description}
\item[sound] the key names the exact Python version. That can be
  setup-python's \texttt{python-version} \emph{output}, \texttt{pythonLocation},
  a full \texttt{3.X.Y} version or a matrix of them, or a value computed from
  \texttt{python -{}-version}. A cached folder whose path contains the Python
  install location also counts, through the hidden version.
\item[minor\_only] the key has the version only down to the minor release,
  for example \texttt{matrix.python-version} set to \texttt{"3.12"}.
\item[no\_interpreter] the key has no Python version at all.
\item[version\_file] the key hashes \texttt{.python-version} or a similar
  file. That is sound only if the file pins a patch release, and the workflow
  alone cannot tell us.
\end{description}
Two details matter in practice. When a key uses an environment variable, we
judge it by the variable's value. When an earlier \texttt{run} step builds the
key, we judge it by that step's script. Each rule has a unit test in
\texttt{tests/}. Table~\ref{tab:val} reports how often the classifier agreed
with hand labels.

The same classifier doubles as a linter:
\begin{center}
\texttt{python -m cachekeys lint .github/workflows}
\end{center}
It flags a built-environment cache whose key lacks the exact Python version.
It is an error if the workflow also skips the install step on a hit, and a
warning otherwise. The fix is one expression in the key:
\texttt{\$\{\{ env.pythonLocation \}\}}. setup-python sets it, and on GitHub's
hosted runners it holds both the exact version and the architecture, for
example \texttt{/opt/hostedtoolcache/Python/3.12.14/x64}. setup-python's
\texttt{python-version} output also pins the version, but not the
architecture.

\section{Study Design}

\paragraph{RQ1: How often do these keys leave out the Python version?}
We drew repositories from GitHub search. We kept Python repositories that
were not forks or archived and had a push in the twelve months before
26 September 2026. We split them into four groups by star count (10--99,
100--999, 1,000--9,999, 10,000+) and ran one search per creation year in each
group, keeping at most the first 300 results. That gave \ck{h.frame_size}
repositories. From those we drew a random sample, with a fixed seed, of up to
1,000 per group: \ck{h.repos_sampled} in all. The 10,000+ group had only
\ck{h.frame_s4} repositories, so we took all of them. For each repository we
downloaded every file in \texttt{.github/workflows} at the latest commit on
the default branch, and classified every step that restores a cache. All
\ck{h.repos_retrieved} repositories were retrieved. The commit IDs are
recorded, and every workflow file that uses
\texttt{actions/cache} is committed to our repository.

\paragraph{RQ2: What happens when such a key matches?}
Our workflow \texttt{harm.yml} runs on \texttt{ubuntu-24.04}. A \emph{seed}
job builds an environment and saves it to the cache. A \emph{restore} job then
restores it under a key we control and runs a single test. The test imports
PyYAML, which contains compiled code, and records which Python ran it. We test
pip with \texttt{venv}, Poetry~2.5.1 with the environment inside the project,
and uv~0.12.19. Each uses its standard commands (\texttt{python -m venv} and
\texttt{pip install}, \texttt{poetry install}, \texttt{uv sync}). There are
five conditions:
\begin{description}
\item[C0] a sound key, with the environment built on 3.12.10 and restored on
  the image's 3.12, so the exact key misses. This is the negative control.
\item[C1] a sound key, with the environment built and restored on the same
  Python, so the exact key hits. This is the positive control.
\item[E1] only the minor version in the key. The environment is built on
  3.12.10, which setup-python downloads in the seed job because the image does
  not carry it, and restored on the image's current 3.12.
\item[E2] no version in the key. The environment is built on 3.11 and
  restored in a job set up for 3.13.
\item[E3] a sound key, plus a restore key without the version. The exact key
  misses, the prefix restores the 3.11 environment, and the install step runs.
\end{description}
As in the action's documentation, the install step is skipped when
\texttt{cache-hit} is \texttt{'true'}. Each outcome file also records the
install step's own output. Each result falls into one of four groups:
\emph{correct} (tests ran on the Python the job asked for, after a hit or a
miss),
\emph{self-healed} (the tool rebuilt the environment by itself), \emph{loud
failure} (the test step failed), or \emph{silent wrong} (the test step passed
on a different Python). The test passes on any Python that can import its
packages. So \emph{silent wrong} applies to code that runs the same on both
versions; a test suite that used features of the newer version would fail
loudly instead. We ran the whole workflow \ck{t3.runs} times. Every action is
pinned to an exact commit.

\paragraph{RQ3: Do maintainers run into it?}
For each workflow file in the sample that caches a built environment, we read
its 40 most recent commits (fewer if it had fewer) and pulled out every
edited \texttt{key:} line. A change \emph{adds the interpreter} if the new key has a
more exact Python version than the old one. It is a \emph{manual bust} if the
two keys differ only in a counter, such as \texttt{v1} to \texttt{v2}. That is
the CI version of \texttt{make clean}: it throws the cache away without saying
what was wrong with it. If the number that changed is a version, such as
\texttt{3.8} to \texttt{3.9}, we call it a \emph{version literal} change.

When they do, the key usually leaves out the Python version

How many of these keys can actually cause the harm RQ2 shows? The
experiment found two routes: restoring an environment and then skipping the
install step, and a fallback key that restores an environment even when the
exact key misses. \ck{h.unsound_with_skip_or_restore_keys} of the
\ck{h.unsound_steps} incomplete keys use at least one of them, and
\ck{h.repos_exposed} repositories (\ck{h.repos_exposed_pct_of_built_env_repos}\%)
have an incomplete key that skips the install step. The silent-wrong result
also needs the same key to be used by jobs on different Python versions. We
can see one way that happens in a single snapshot: one key shared across a
matrix of Python versions, with no other matrix variable in the key to tell
them apart. That occurs in only \ck{h.shared_across_python_steps} steps, in
\ck{h.shared_across_python_repos} repositories.

We checked each of the four against its public CI logs
(\texttt{scripts/check\_wild.py}; the evidence is committed under
\texttt{data/wild/} because GitHub deletes run logs). \ck{w.inert_shared_caches}
are inert: in one the cached folder never exists, and in the other the cached
\texttt{.venv} is never created, because dependencies go into setup-python's
interpreter and the tests run in Hatch's own environment. For
\ck{w.undetermined_shared_caches} the workflow has changed since our snapshot,
so its logs cannot settle it. The remaining one is live. In
\href{https://github.com/jacebrowning/gitman/actions/runs/35938984458}{a
successful run of gitman's CI} on 24 September 2026, one \texttt{.venv} cache
was restored into all \ck{w.wild_jobs_in_live_run} matrix jobs. The jobs set
up Python 3.10, 3.11, 3.13 and 3.14, but in each of those
\ck{w.wild_jobs_wrong_python} jobs the tests ran on
\ck{w.wild_tests_ran_on}, and all of them passed. The install step ran, and
Poetry reported ``No dependencies to install or update''. This is the E2
failure in a real project, with the install step not even skipped.

The other way a key ends up shared across Python versions, a project moving to a new Python
version without changing its lock file, cannot be seen in one snapshot, so the
count of four is a lower bound. Minor-only keys that skip the install step
(\ck{h.minor_only_with_skip}) are set up for the E1 failure at the next patch
release.

Skipping the install step on a hit is \emph{more} common with sound keys
(\ck{h.sound_with_skip} of \ck{h.sound_steps}) than with incomplete ones
(\ck{h.unsound_with_skip} of \ck{h.unsound_steps}). About half of the
incomplete keys come with restore keys instead
(\ck{h.unsound_with_restore_keys} of \ck{h.unsound_steps}). Those restore an
environment even when the exact key misses. RQ2 shows that does not make them
safe. The exact E3 setup, a sound key whose fallback drops the version,
appeared \ck{h.sound_steps_with_restore_key_fallback_hazard} times in the
sample. As for why sound keys skip the install step more often, one possible
reading, which we did not test, is that maintainers who think carefully about
their keys also optimise their installs.

Table~\ref{tab:harm} shows the results. All \ck{t3.runs} runs agreed in every
cell. Both controls worked as they should. With C0 each tool missed the
cache, rebuilt, and tested on the Python the job asked for. With C1 each tool

\emph{With no version in the key (E2), every tool produced a passing build on
the wrong Python.} The job asked for \ck{t3.E2_pip_asked}. The restored
environment still pointed at \ck{t3.E2_pip_ran_on}, which the image also
carries, so the tests ran there and passed. uv printed no warning and reused
the environment. It was a working environment that met the project's
\texttt{requires-python}, so there was nothing obviously wrong for uv to
catch. The test output under all three tools is just \texttt{1 passed}, and the
job's setup step reports the Python it was asked for.

\emph{With only the minor version (E1), a patch release broke the build under
pip and Poetry.} The environment pointed at the 3.12.10 install, which the
image no longer has. Under pip the test command failed with \emph{cannot
execute: required file not found}. Poetry saw the environment was broken and
recreated it, but the install step had been skipped, so \texttt{pytest} was
missing. uv spotted the broken link, rebuilt the environment and passed. A
failure like this is visible, but someone still has to work out why. One
fix is to change the key, which RQ3 looks at.


\emph{A restore key without the version (E3) gave pip the wrong Python even
though the install step ran.} Running \texttt{python -m venv .venv} over an
existing environment did not replace its interpreter link, and
\texttt{pip install} reported every requirement as already satisfied (the
install output is in each E3 outcome file). Poetry and uv
rebuilt the environment during the install step. For Poetry that depends on
how it is called: our install step runs \texttt{poetry env use} with the job's
interpreter first. gitman's plain \texttt{poetry install} kept the restored
environment (\S\ref{sec:rq1}). So skipping the install step
is not the only way an incomplete key does harm. With pip, restoring the
environment at all is enough.

\label{sec:rq3}

evidence is in the commit messages. We went through

\ck{rq3.key_changes} separate changes to a cache key, in

(\ck{rq3.commits_in_two_categories} commits fall into two of the categories
below). A change that merge commits
repeat is counted once. \ck{rq3.commits_adds_interpreter} commits in
\ck{rq3.repos_with_adds_interpreter} repositories added a Python version to a
key or made it more exact. Several say so in the commit message:
\href{https://github.com/andreoliwa/nitpick/commit/731d6ebb36a3e3ac39d2574e1abb468b59f0ffe1}{``ci: include Python version in cache key''},
\href{https://github.com/eigenein/protobuf/commit/befb022dcdc84f5ab9936ca793a27d2776a2c015}{``Fix: use OS and Python version in the cache's key''},
and, closest to condition E1,
\href{https://github.com/python-zeroconf/python-zeroconf/commit/0e201f781c96ea77b7388f306f54b21101c6833f}{``ci: key venv cache on resolved python patch version''}.
That last one swaps \texttt{matrix.python-version} for setup-python's output,
which is the fix our linter suggests.

\ck{rq3.commits_manual_bust} commits in \ck{rq3.repos_with_manual_bust}
repositories were manual busts. In \ck{rq3.repos_with_increment_comment} of
those repositories the key carries a permanent comment,
\texttt{\# increment to reset cache}. Resetting by hand is part of how they
work. Another \ck{rq3.commits_version_literal} commits changed a version
number typed into the key, for example from \texttt{py3.9} to
\texttt{py3.12}. The other \ck{rq3.commits_other} commits made other kinds of
edits. Every change links to its commit in
\texttt{results/rq3\_key\_changes.csv}.

These counts are small, and commit messages rarely say what went wrong. A few,
like the three quoted above, show maintainers running into this. They also
fix it in different ways: some add the Python version to the key, and some
bump a counter each time.

\section{What To Do About It}

\paragraph{For maintainers.} Put the Python version the job actually got, and
the CPU architecture, into the key. \texttt{\$\{\{ env.pythonLocation \}\}}
covers both on GitHub's hosted runners. The fix costs little: an exact-version
key misses once each time the runner image moves to a new patch release, and
hits otherwise. A \texttt{matrix} value like
\texttt{"3.12"} is what the job \emph{asked for}. It is not necessarily what got
\emph{installed}. Restore keys need it too.

Caching only the package manager's download folder, and rebuilding the
environment each time, would also avoid the problem. It needs no Python
version in the key, but it is not free. We timed it (\texttt{bench.yml}): a typical
data-project stack of 12 pinned packages, three strategies, three tools, five
runs each, \ck{t4.timed_jobs} timed jobs in all. Table~\ref{tab:bench} shows
the time from the cache restore to the end of the install step. For pip,
restoring the built environment took \ck{t4.pip_venv_median_s}~s, and rebuilding
from the download cache took \ck{t4.pip_download_median_s}~s. For Poetry it was
\ck{t4.poetry_venv_median_s}~s against \ck{t4.poetry_download_median_s}~s.
For pip the download cache barely helped at all:
\ck{t4.pip_download_median_s}~s, against \ck{t4.pip_none_median_s}~s with no
cache. uv
was fast every way: \ck{t4.uv_none_median_s}~s with no cache at all. So for pip
and Poetry, caching the built environment is worth keeping, with the exact
Python version in the key. For uv, caching the environment gains little.

\paragraph{For tool builders.} Workflow linters check syntax, types and
security. Neither of the two we looked at (actionlint and zizmor) checks
whether a key is complete. zizmor's cache check is about cache poisoning in
release workflows. The check is small, and ours is available. uv's behaviour
in E1 shows an installer can check the interpreter link before trusting a
restored environment. In E2 no such check would have helped, because the
environment was valid, just for a different Python.

\section{Limits of This Study}

\emph{The classifier.} It reads workflow text with patterns. It does not follow
keys set inside reusable workflows or composite actions, and it can misread
unusual folder names. It sees only the workflow text, so it cannot tell whether
a cached folder is ever populated or used by the tests. Some counted caches
may be inert, as two of the four we checked by hand were. We checked it against hand labels in two rounds of 100
cache steps each, drawn at random with fixed seeds and with no step in both.
In round 1 the labeller worked from a shortened version of the rules that left
out several kinds of built environment. Agreement was
\ck{t5r1.path_kind_agreement_pct}\% on folder type and
\ck{t5r1.verdict_agreement_pct}\% on the verdict, and the round exposed one
classifier bug, which we fixed. Round 2 used the full rules, shown on screen
for every step (Table~\ref{tab:val}). Where both the label and the classifier
said the step stores a built environment, the verdict agreed on
\ck{t5.verdict_both_built_env_agree} of \ck{t5.verdict_both_built_env_n}
(\ck{t5.verdict_both_built_env_pct}\%). Over all 100 steps, agreement was
\ck{t5.path_kind_agreement_pct}\% on folder type and
\ck{t5.verdict_agreement_pct}\% on the verdict, against round 1's
\ck{t5r1.verdict_agreement_pct}\%. We
then checked each of the \ck{t5.disagreements_checked} disagreements against
the written rules. In \ck{t5.disagreements_tool_follows_rubric} the rules
support the classifier. \ck{t5.disagreements_classifier_error} was a
classifier error: a rule counts \texttt{\textasciitilde/.local/bin} as a Python
environment, and one step cached a non-Python program there. In
\ck{t5.disagreements_undecidable} the workflow file alone cannot settle it.
Each call, with the rule it rests on, is in
\texttt{data/validation/adjudication\_round2.csv}. We did not change the
classifier after seeing the round 2 labels. Two caveats: the labels come from
one person, the author, and the disagreements were checked by the tool's
author, so neither step is independent. A second, independent labeller would
make this check stronger.
\emph{The experiments.} The main experiment uses one test project, one runner
image, one date and fixed tool versions. The results matched across runs, but
other versions of these tools may behave differently. The timings in
Table~\ref{tab:bench} come from one set of packages on one day, and runner
timing is noisy, so treat them as rough sizes. \emph{The sample.} It comes from
GitHub search, which returns at most 300 results per query, so it is not a
uniform sample of GitHub. We saw each workflow only at its latest commit, and
the history study read at most 40 commits per file. We only looked at Python.
The silent-wrong result depends on GitHub's current practice of keeping several
minor versions of Python on each runner image. If an image carried only one,
E2 would become a loud failure like E1.
The same problem may apply to \texttt{node\_modules} with compiled add-ons and
to Rust's \texttt{target/} folder. We did not check.

\section{Related Work}

\emph{Build correctness.} \citet{mokhov2018build} give a formal model of build
systems, including when a build is correct. \citet{licker2019incorrect} find
missing dependencies in build rules: they change files, run incremental
builds, and compare what changed with what should have changed. Our
experiment uses a similar idea: change one input, the Python version, and see
what the cached environment does. \citet{zheng2025hermeticity}
study hermeticity in Bazel builds.

\emph{CI caching.} \citet{gallaba2022kotinos} infer build dependencies inside a
CI service and cache whole build environments, so that correctness does not
depend on hand-maintained dependency declarations. We study the hand-written
case they avoid. \citet{hasan2026caching} study how GitHub Actions projects
adopt and change their caching setup. There, key changes show up as
maintenance, and a badly designed key is described as causing repeated misses.
\citet{urdih2026smells} list ten cache smells in GitLab CI. Nine are about
speed or storage. The tenth, \emph{No Fallback Cache}, recommends adding
fallback keys. Our E3 condition shows that a fallback key without the Python
version can restore the wrong environment. \citet{ghaleb2026travis} measure what caching gains on
Travis CI, and \citet{bouzenia2024resource} find caching under-used in GitHub
Actions. \citet{khatami2024smells} list workflow smells. Their one caching
smell is about the \texttt{cache} option of setup actions. Our question, whether
a key covers what the cached folder depends on, is the correctness side of
this work.

\section{Conclusion}

A cache key for a built environment is a list of what it depends on, and most
of the ones we sampled leave out the Python version. When such a key matches,
the result depends on the tool and on what changed. It can be a loud failure,
a quiet repair, or a passing build on the wrong Python. The fix is one
expression, and for pip and Poetry it keeps the time the cache saves.
