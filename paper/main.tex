\begin{abstract}
A GitHub Actions workflow that caches a built Python environment and restores
it on a key match is running an incremental build. The cache key is its only
declaration of what that environment depends on. Build-systems research treats
an incomplete dependency declaration as a correctness bug. Research on CI
caching has measured adoption, speed and configuration smells. We study the
point where the two meet. We state a soundness condition for cache keys of
built environments and check it on a stratified sample of
\ck{h.repos_sampled} Python repositories. Of \ck{h.built_env_steps} cache steps
that store a built environment, \ck{h.unsound_steps}
(\ck{h.unsound_pct_of_built}\%) use a key that omits the exact interpreter
version, in \ck{h.repos_any_unsound} of the \ck{h.repos_caching_built_env}
repositories that cache one. A controlled experiment on GitHub-hosted runners
shows what such a key does when it matches. A key without the interpreter
version let a job configured for Python~3.13 run its tests on Python~3.11 and
pass, under pip, Poetry and uv alike. A key with only the minor version broke
the build after a patch release under pip and Poetry; uv repaired the
environment. We release a linter for these keys. Code, data, and every number
in this paper: \repourl.
\end{abstract}

\section{Introduction}

Continuous integration services let a workflow save a directory at the end of
a job and restore it at the start of a later one. On GitHub Actions this is
the \texttt{actions/cache} action. A step names the directory, gives a key,
and exposes whether the key matched. The action's own documentation shows
the next step: skip installation when the key matched~\cite{actionscache}.

For a cache of downloaded packages, a loose key costs little. Package
managers verify what they download, and install runs anyway. For a cache of
a \emph{built} environment the case differs. A Python virtual environment
records the interpreter it was created from, and its \texttt{python} is a link
into that interpreter's installation. Compiled extensions inside it target
that interpreter's ABI. Restoring it under a different interpreter restores a
build whose inputs changed. The cache key decides whether that happens.

This is the problem build-systems research calls an incorrect or incomplete
dependency declaration~\cite{mokhov2018build,licker2019incorrect}. In Bazel it
is hermeticity~\cite{zheng2025hermeticity}. A build is correct only if every
input to a cached result is part of the key it is looked up by. Studies of CI
caching ask other questions. They ask how caching is adopted and
maintained~\cite{hasan2026caching}, whether it saves
time~\cite{ghaleb2026travis,bouzenia2024resource}, and which configuration
smells waste storage or cause misses~\cite{urdih2026smells,khatami2024smells}.
We found no study that asks whether a CI cache key covers what the cached
directory depends on.

We make four contributions.
\begin{enumerate}
\item A soundness condition for cache keys of built Python environments, and
  a classifier and linter that apply it to workflow files (\S\ref{sec:sound}).
\item A measurement on a stratified sample of \ck{h.repos_sampled} Python
  repositories: how often built environments are cached, and how often the
  key omits the interpreter (\S\ref{sec:rq1}).
\item A controlled experiment that restores such caches under pip, Poetry and
  uv on GitHub-hosted runners and records what each run actually tested
  (\S\ref{sec:rq2}).
\item A history study of how maintainers change these keys
  (\S\ref{sec:rq3}).
\end{enumerate}

\section{Background}
\label{sec:bg}

\paragraph{Matching in \texttt{actions/cache}.}
A cache step has a \texttt{key} and optional \texttt{restore-keys}. If an entry
with exactly \texttt{key} exists, it is restored and the output
\texttt{cache-hit} is \texttt{'true'}. Otherwise each restore key is tried as a
prefix, newest entry first. A prefix match restores files but sets
\texttt{cache-hit} to \texttt{'false'}. Each entry also carries a
\emph{version}, a hash of the compression tool and the list of cached paths.
Entries with a different version never match, so a Windows cache is never
restored on Linux~\cite{actionscache}.

\paragraph{What a virtual environment depends on.}
On GitHub-hosted runners, \texttt{actions/setup-python} places each interpreter
under \texttt{/opt/hostedtoolcache/Python/X.Y.Z/}. The image in our runs
(\texttt{ubuntu-24.04}, version 20260920.314.1) carried exactly one patch
release per minor version: 3.10.21, 3.11.16, 3.12.14, 3.13.15 and 3.14.7
(recorded in every outcome file under \texttt{data/harm/}). A virtual
environment built on 3.12.10 links to
\texttt{/opt/hostedtoolcache/Python/3.12.10/x64/bin/python}. That path does not
exist on this image. An environment built on 3.11 links to
the 3.11 installation. That one does exist on an image that also carries
3.13, since images carry several minor versions.

\section{A Soundness Condition for Cache Keys}
\label{sec:sound}

A cache step is \emph{sound} for a cached path if its key, together with the
path list folded into the cache version, determines every input the contents
of that path depend on. For a built Python environment those inputs are the
exact interpreter, the dependency specification, and the platform. The
dependency specification is usually present, as a hash of a lock file. The
platform is partly covered by the cache version. We therefore focus on the
interpreter.

Our classifier (\texttt{cachekeys/analyze.py}) first decides what a cache step
stores. A \emph{built environment} is a virtual environment (\texttt{.venv},
\texttt{venv*}, Poetry's \texttt{virtualenvs}), \texttt{.tox}, \texttt{.nox},
\texttt{site-packages}, the target of \texttt{pip install -{}-user}, or the
interpreter's own installation directory. A \emph{download store} is a package
manager's download cache. For built environments it assigns one verdict:
\begin{description}
\item[sound] the key names the exact interpreter: setup-python's
  \texttt{python-version} \emph{output}, \texttt{pythonLocation}, a full
  \texttt{3.X.Y} literal or a matrix of them, or a value computed from
  \texttt{python -{}-version}. A cached path that embeds the interpreter
  location also counts, through the cache version.
\item[minor\_only] the key carries the version only to the minor release, for
  example \texttt{matrix.python-version} with values like \texttt{"3.12"}.
\item[no\_interpreter] the key carries no Python version.
\item[version\_file] the key hashes \texttt{.python-version} or a similar
  file. It is sound only if that file pins a patch release, which the
  workflow text does not show.
\end{description}
Two refinements matter in practice. Keys built from environment variables are
judged by the variable's value. Keys computed in an earlier \texttt{run} step
are judged by that step's script. Unit tests for each rule are in
\texttt{tests/}; the classifier's agreement with hand labels is reported in
Table~\ref{tab:val}.

The same classifier is the linter:
\begin{lstlisting}
$ python -m cachekeys lint .github/workflows
\end{lstlisting}
It reports a built-environment cache without the exact interpreter as an
error when installation is skipped on a hit, and as a warning otherwise. The
fix is one expression in the key:
\texttt{\$\{\{ steps.<setup-python id>.outputs.python-version \}\}}.

\section{Study Design}

\paragraph{RQ1: How often do cache keys for built environments omit the interpreter?}
We built a sampling frame from GitHub repository search. The queries
selected Python repositories that were neither forks nor archived and had
been pushed in the twelve months before 26 September 2026. We ran one query
per creation year in each of four star strata (10--99, 100--999,
1,000--9,999, 10,000+) and kept the first 300 results of each. The frame
holds \ck{h.frame_size} repositories. We drew a seeded random sample of up to
1,000 per stratum, \ck{h.repos_sampled} in total. For each we fetched every
workflow file at the default branch's HEAD commit and classified every
\texttt{actions/cache} restore step. Commit SHAs are recorded, and the text of
every workflow file that uses \texttt{actions/cache} is committed.

\paragraph{RQ2: What happens when such a key matches?}
The workflow \texttt{harm.yml} runs on \texttt{ubuntu-24.04}. A \emph{seed} job
builds an environment and saves it. A \emph{restore} job then restores it
under a controlled key and runs a test suite with one test. The test imports
PyYAML, which has a compiled extension, and records the interpreter it ran
on. We test pip with \texttt{venv}, Poetry~2.5.1 with an in-project
environment, and uv~0.12.19, each in the idiom its documentation shows. There
are four conditions:
\begin{description}
\item[C0] sound key, the control;
\item[E1] minor-only key, with the environment seeded on 3.12.10 and restored
  on the image's current 3.12;
\item[E2] no version in the key, with the environment seeded on 3.11 and
  restored in a job set up for 3.13;
\item[E3] sound key, but a restore key that drops the version. The exact key
  misses, the prefix restores the 3.11 environment, and installation runs.
\end{description}
Installation is skipped when \texttt{cache-hit} is \texttt{'true'}, as the
action's documentation shows. Each outcome falls in one class:
\emph{correct} (tests ran on the requested interpreter),
\emph{self-healed} (the tool rebuilt the environment on its own),
\emph{loud failure} (the test step failed), or \emph{silent wrong} (the test
step passed on a different interpreter). We ran the workflow
\ck{t3.runs} times. All actions are pinned by commit SHA.

\paragraph{RQ3: How do maintainers change these keys?}
For every workflow file in the sample that caches a built environment, we
read up to 40 commits of its history and extracted every change to a
\texttt{key:} line. A change \emph{adds the interpreter} if the new key carries
a stronger version signal than the old one. It is a \emph{manual bust} if the
two keys differ only in a number, as in \texttt{v1} to \texttt{v2}. That is the
CI form of \texttt{make clean}: it discards the cache without saying what was
wrong with it. If the changed number is a version (\texttt{3.8} to
\texttt{3.9}), the change is a \emph{version literal} update instead.

Table~\ref{tab:harm} gives the outcomes. All \ck{t3.runs} runs agreed in every
cell. The control (C0) behaved as intended: each tool missed the cache, rebuilt,
and tested on the requested interpreter.

\emph{A key with no version (E2) produced a passing build on the wrong
interpreter under every tool.} The job was set up for
\ck{t3.E2_pip_asked}. The restored environment linked to
\ck{t3.E2_pip_ran_on}, which the runner image also carries, and the tests ran
there and passed. uv did not intervene, because the environment was valid and
satisfied the project's \texttt{requires-python}. Nothing in the log shows the
mismatch unless one reads the interpreter path.

\emph{A minor-only key (E1) failed loudly under pip and Poetry after a patch
release.} The environment linked to the 3.12.10 installation, which the image
no longer carries. Under pip the test command failed with \emph{cannot
execute: required file not found}. Poetry detected that the environment was
broken and recreated it, but installation had been skipped, so
\texttt{pytest} was missing. uv detected the dangling interpreter, rebuilt the
environment and passed. A failure of this kind is visible, but a maintainer
has to find its cause. The usual repair is to change the key, which RQ3
examines.

\emph{A restore-key fallback (E3) produced the wrong interpreter under pip even
though installation ran.} Running \texttt{python -m venv .venv} over an existing
environment did not replace its interpreter link, and \texttt{pip install}
reported the requirements as satisfied. Poetry and uv rebuilt the environment
during installation. Skipping installation on a hit is therefore not the only
way an unsound cache causes harm. Under pip, restoring the environment is
enough.

\subsection{RQ3: How keys change}
\label{sec:rq3}

We scanned \ck{rq3.workflow_files_scanned} workflow files and found
\ck{rq3.key_changes} distinct changes to a cache key, in
\ck{rq3.repos_with_any_key_change} repositories. We count a change once even
when merge commits repeat it. \ck{rq3.commits_adds_interpreter} commits in
\ck{rq3.repos_with_adds_interpreter} repositories added an interpreter version
to a key or made it more exact. Several say so in their message:
\href{https://github.com/andreoliwa/nitpick/commit/731d6ebb36a3e3ac39d2574e1abb468b59f0ffe1}{``ci: include Python version in cache key''},
\href{https://github.com/eigenein/protobuf/commit/befb022dcdc84f5ab9936ca793a27d2776a2c015}{``Fix: use OS and Python version in the cache's key''},
and, closest to condition E1,
\href{https://github.com/python-zeroconf/python-zeroconf/commit/0e201f781c96ea77b7388f306f54b21101c6833f}{``ci: key venv cache on resolved python patch version''}.
That last commit replaces \texttt{matrix.python-version} with setup-python's
output, the fix our linter proposes.

\ck{rq3.commits_manual_bust} commits in \ck{rq3.repos_with_manual_bust}
repositories were manual busts. In \ck{rq3.repos_with_increment_comment} of them the key carries a standing
comment, \texttt{\# increment to reset cache}, so invalidation by hand is part
of the design. Another \ck{rq3.commits_version_literal} commits changed a
version number written into the key by hand, for example from
\texttt{py3.9} to \texttt{py3.12}. The remaining \ck{rq3.commits_other} commits
made other edits: renames, lock-file changes, and restructuring. Every change
links to its commit in \texttt{results/rq3\_key\_changes.csv}.

These counts are small, and a commit message rarely says what went wrong. They
show that maintainers do meet this problem, and that the repair varies:
some add the interpreter to the key, and others bump a counter each time.

\section{Implications}

\paragraph{For maintainers.} Put the interpreter the job actually got into
the key. setup-python reports it as an output. A \texttt{matrix} value such as
\texttt{"3.12"} is what was \emph{requested}, which differs from the
interpreter that was \emph{installed}. The same applies to restore keys.
Alternatively, cache the package manager's download store and let the
environment be rebuilt; that needs no interpreter in the key.

\paragraph{For tool builders.} Linters for workflows check syntax, types and
security. None of those we examined (actionlint, zizmor) checks key
completeness; zizmor's cache audit concerns cache poisoning in release
workflows. The check is small, and our implementation is available. uv's
behaviour under E1 shows that an installer can check the interpreter link
before trusting a restored environment. Under E2 no installer check helped,
because the environment was valid for a different interpreter.

\section{Threats to Validity}

\emph{Construct.} The classifier reads workflow text with patterns. It does
not follow keys set in reusable workflows or composite actions, and it may
misjudge unusual paths. We report its agreement with hand labels
(Table~\ref{tab:val}). \emph{Internal.} The experiment uses one fixture, one
runner image, one date and pinned tool versions. Its outcomes were identical
across runs, but other versions of these tools may behave differently.
\emph{External.} The frame comes from repository search, capped at 300
results per query, so it is not a uniform sample of GitHub. We study Python
only. The same condition applies to \texttt{node\_modules} with native addons
and to Rust's \texttt{target/} directory, which we did not measure.

\section{Related Work}

\emph{Build correctness.} \citet{mokhov2018build} give a model in which a build
system is correct only if a cached result is looked up by all its inputs.
\citet{licker2019incorrect} detect missing dependencies in build rules by
changing inputs and comparing incremental and clean builds, the approach our
experiment applies to CI caches. \citet{zheng2025hermeticity} study
hermeticity in Bazel-based builds.

\emph{CI caching.} \citet{hasan2026caching} study how GitHub Actions
repositories adopt and change caching configuration. Key changes appear
there as maintenance, and a badly designed key is described as causing
repeated misses. \citet{urdih2026smells} catalogue cache smells in GitLab CI,
all concerned with efficiency and retention. \citet{ghaleb2026travis} measure
the benefit of caching on Travis CI, and \citet{bouzenia2024resource} find
under-used caching in GitHub Actions. \citet{khatami2024smells} catalogue
workflow smells; their one caching smell concerns the \texttt{cache} parameter
of setup actions. Our question, whether a key covers what the cached
directory depends on, is the correctness side of this work.

\section{Conclusion}

A cache key for a built environment is a dependency declaration, and most of
the ones we sampled leave out the interpreter. When such a key matches, the
outcome depends on the tool and on which input moved. It can be a loud
failure, a silent repair, or a passing build on the wrong interpreter. The
fix costs one expression.
